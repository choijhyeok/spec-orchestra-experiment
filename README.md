# Spec Orchestra Experiment

명세 기반 병렬 개발 방식에 세 규칙을 더했을 때의 결과를 비교한 **단일 소규모 합성 웹앱 실험**입니다. 설치 가능한 완성 orchestration 제품이나 자동 실행기가 아닙니다. 원본 플러그인을 설치해 실행한 평가도 아닙니다. 공개된 지침을 호스트 도구에 맞게 재현했습니다.

**이번 사례에서는 품질 개선이나 재작업 감소를 입증하지 못했습니다.**

| 측정 | A · 기존 방식 재현 | B · 세 규칙 보완 |
|---|---:|---:|
| 동일 독립 API·브라우저 검증 | 19/19 | 19/19 |
| UI 일관성 6항목 | 6/6 | 6/6 |
| 구형 명세 제출 / 승인·유입 | 0 / 0 | 0 / 0 |
| 검토 후 결함 수정 라운드 | 0 | 0 |
| 공통 대기 제외 경과 | 12분 53초 | 12분 48초 |
| 전체 에이전트 수 | 5 | 4 |
| 관리·증거 텍스트 줄 수 | 1,009 | 1,429 |

A도 공통 UI 조정과 통합 브라우저 검증을 자발적으로 수행했습니다. B는 실행 가능한 공통 기준 UI 선행, 명세 변경 영향·버전 관리, 통합 실사용 UI 검증을 필수로 추가했습니다.

A의 5명은 **메인 1 + 기능 구현자 2 + 기능별 독립 검토자 2**입니다. B의 4명은 **메인 1 + 기능 구현자 2 + 두 기능을 순서대로 검토한 독립 검토자 1**입니다. 양쪽 모두 명세 준수 판정 후 코드 품질 판정을 별도로 남겼습니다. 동시 구현자 한도는 같았지만 검토자 구성은 달랐으므로 시간·기록량 차이를 세 규칙의 인과 효과로 해석할 수 없습니다.

**수정 0회는 검토 피드백이나 독립 평가 이후의 결함 수정만 뜻합니다.** 두 조건 모두 계획된 v1→v2 변경을 받아 두 기능을 다시 구현했습니다. 조건별 정상 v2 기능 구현 커밋 2개는 결함 재작업 횟수에서 제외했습니다. 관리 기록량도 원래 실험에서 집계한 수치이며, 이 공개 저장소의 파일 수나 줄 수가 아닙니다.

## 앱 실행

Python 3.9 이상이면 외부 패키지 없이 실행할 수 있습니다. 합성 데이터만 쓰며, 서버가 살아 있는 동안 메모리에 저장됩니다. 디스크 영속성·인증·배포는 구현 범위가 아닙니다.

```sh
python3 apps/A/server.py --port 8131
```

브라우저에서 `http://127.0.0.1:8131/create` 또는 `/requests`를 엽니다. B는 별도 터미널에서 실행합니다.

```sh
python3 apps/B/server.py --port 8141
```

B의 공통 기준 화면은 `http://127.0.0.1:8141/baseline`입니다. 서버는 `Ctrl+C`로 종료합니다. A/B 서버의 상태는 서로 독립입니다.

```sh
cd apps/A
python3 -m unittest discover -s tests -v
```

B의 테스트도 `apps/B`에서 같은 명령으로 실행합니다. 원래 통합 상태에서 A 13개, B 9개 단위 테스트가 통과했습니다. 테스트 개수 차이는 품질 점수로 사용하지 않았습니다.

## 공개 스냅샷 재검증

앱 실행에는 Node나 Playwright가 필요하지 않습니다. 독립 브라우저 평가를 직접 다시 확인하려면 Node 18 이상에서 공식 npm Playwright와 Chromium을 준비합니다.

```sh
npm install --ignore-scripts
npx playwright install chromium
npm run verify:a
npm run verify:b
```

새 결과는 Git에서 제외되는 `verification-output/`에 저장됩니다. 이 명령은 공개된 앱 스냅샷의 재검증이며 원래 에이전트 비교 실험을 다시 실행하지 않습니다. 기존 호환 Chromium을 쓰려면 `PLAYWRIGHT_CHROMIUM_EXECUTABLE` 환경 변수로 실행 파일 경로를 지정할 수 있습니다. 원본 평가 코드의 경로를 제거한 참고본은 [여기](evidence/original-evaluator.cjs.txt)에 보존했습니다.

`fixture/`는 동일 초기 커밋의 파일 스냅샷입니다. 기능 미구현 API는 501을 반환합니다. 최종 앱은 `apps/A`, `apps/B`에 있으며 원본과 파일 바이트가 같습니다. 공개용 평가 도구는 패키지와 브라우저 경로만 이식 가능하게 조정했습니다. 원래 사전등록 해시는 원본 파일에 대한 기록이며 공개용 도구의 동일 해시를 주장하지 않습니다.

## 실험의 한계

- 비맹검 단일 사례, 기능 2개, 작은 메모리 저장소입니다. 일반적 우월성·통계적 유의성을 주장하지 않습니다.
- 변경은 두 v1 최초 후보가 준비된 뒤 최종 검토·통합 전에 전달했습니다. 실행 중 변경 경쟁이나 오래된 제출 유입을 충분히 시험한 것은 아닙니다. 실패나 구형 제출을 인위적으로 주입하지 않았습니다.
- 요청 모델은 모든 역할에서 `gpt-6.1-sol/high`였고 도구 호출은 수락됐지만 실제 backend model/reasoning의 독립 확인 정보는 노출되지 않았습니다.
- 토큰·금액·정확한 CPU 시간·인프라 승인 대기 비용은 미측정입니다. 시간은 각 메인이 기록한 경과이며 공통 대기 종료를 같은 변경 공개 시각으로 맞췄습니다.
- A/B의 자율 선택, 검토자 수, 테스트 수, 기록 형식이 달랐습니다. 이번 결과는 세 보완 규칙 각각의 순수 효과나 비용을 분리하지 못합니다.

현재 근거로는 대규모 전용 실행기보다 작은 체크리스트형 확장을 유지하며 실제 프로젝트에서 반복 검증하는 편을 권합니다.

## 공개 범위와 출처

원본 실험 폴더는 보존했습니다. 이 저장소는 필요한 앱·초기 fixture·계획·결과·보고서·선별한 증거만 담은 새 이력입니다. 원본 중첩 Git 이력과 임시 worktree 메타데이터, 캐시, Library 도우미·식별자, 원시 에이전트 대화, 개인 절대 경로는 포함하지 않았습니다. 공개 증거의 개인 경로는 표시자로 치환했으며 결과 수치는 바꾸지 않았습니다. 원래 커밋 SHA는 출처 식별용이며 이 공개 저장소에서 조회 가능한 커밋이라고 주장하지 않습니다. 보고서의 과거 시점 상태 문구는 실험 완료 당시 기록입니다.

A의 절차는 [wan-huiyan/subagent-driven-development](https://github.com/wan-huiyan/subagent-driven-development/blob/3a020dd96a45ef791f7009f95710fc3bdaadea2d/plugins/subagent-driven-development/SKILL.md)를 참고했습니다. 상류 지침과 라이선스 고지는 [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md)에 있습니다. 제3자 스킬·플러그인·실행기는 vendoring하지 않았습니다.
